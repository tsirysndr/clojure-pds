# S3-compatible blob storage

Set `PDS_BLOB_BACKEND=s3` to store new blob bytes in S3. PostgreSQL still stores
account ownership, CID, MIME type, byte size, bucket, and object key. Existing
PostgreSQL blobs remain readable; switching backends does not migrate old bytes.

| Variable | Default | Purpose |
| --- | --- | --- |
| `PDS_BLOB_BACKEND` | `postgres` | Select `s3` to enable external storage |
| `PDS_S3_BUCKET` | required for S3 | Existing private bucket |
| `PDS_S3_REGION` | `us-east-1` | Signing region |
| `PDS_S3_ENDPOINT` | AWS regional endpoint | Override for compatible providers; HTTPS origin, or loopback HTTP for tests |
| `PDS_S3_FORCE_PATH_STYLE` | `false` | Set `true` for providers requiring `/bucket/key` addressing |
| `PDS_S3_PREFIX` | `blobs` | Object prefix; safe slash-separated segments, or empty |
| `PDS_S3_ACCESS_KEY_ID` | unset | Explicit access key; pair with secret |
| `PDS_S3_SECRET_ACCESS_KEY` | unset | Explicit secret key |
| `PDS_S3_SESSION_TOKEN` | unset | Optional temporary-credential token |

Without explicit credentials the AWS SDK uses its default credential provider
chain (for example `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`, profiles, or
container/instance credentials). Use a bucket with `s3:PutObject` and `s3:GetObject`
permissions for the configured prefix. Runtime does not create buckets, set public
ACLs, or require list/delete permissions. Bucket encryption is configured by the
operator/provider. AWS SDK for Java is pinned in `deps.edn`.

Example for an S3-compatible service:

```sh
export PDS_BLOB_BACKEND=s3
export PDS_S3_BUCKET=pds-blobs
export PDS_S3_ENDPOINT=https://storage.example.com
export PDS_S3_REGION=us-east-1
export PDS_S3_FORCE_PATH_STYLE=true
export PDS_S3_ACCESS_KEY_ID=your-access-key
# Set PDS_S3_SECRET_ACCESS_KEY through your process/secret manager.
mise exec -- clojure -M:run
```

Keys use `<prefix>/<SHA-256 of DID>/<CID>`. Each account has an independent object
namespace. Downloads go through the PDS ownership/status checks, then verify size
and CID; no public bucket URLs or presigned redirects are exposed. Reads are
bounded to the recorded size plus one byte. The existing 5 MiB limit still applies.

Uploads persist bytes before committing the database locator. Duplicate uploads
are serialized across instances; the first MIME type wins. An S3 failure returns
sanitized HTTP 503 and rolls back metadata, without falling back to database bytes.
Missing or corrupted objects also return 503. A crash/rollback after PUT can leave
an unreferenced object: automatic object garbage collection is not implemented.
Back up both the database and bucket; retain the old endpoint and read permissions
for any existing S3 objects. Stored keys/buckets survive prefix/bucket changes,
but endpoint changes require moving those objects to the new service. Disabling
S3 leaves S3-backed records intact and makes their downloads unavailable.

## Verification

```sh
uv run scripts/test-s3.py
```

The script starts isolated Moto 5.2.3 and PostgreSQL instances, then runs the full
suite with extra S3 HTTP tests. It needs `uv` and PostgreSQL binaries (see
`scripts/test-postgres.sh` for `PG_BIN`). Tests cover signed requests, temporary
credentials, path-style keys, binary round trips, reopen/persistence, ownership,
record references, duplicate MIME handling, failed PUT rollback, missing objects,
and corruption/oversize rejection. No live AWS/R2 bucket has been tested or changed.
